# 工程主线：大数据导入、低内存处理与紧凑存储

日期：2026-10-25。状态：**方法验证与下一阶段设计**。已完成16组本机合成基准；这些实验尚未接入 v0.2 获取服务，不代表完成100GB导入、真实ERA5大任务或进程内存硬限制。

目标是让所需数据规模超过机器内存时，仍能按需获取、连续写入、无损保存并局部查询。扩充渠道目录服务于这个目标。

## 先区分三个量

| 量 | 要解决的问题 | 对应方法 |
| --- | --- | --- |
| 运行内存 RAM | 不把整份数据及多个副本装进内存 | 有界分块、流式解码/写入/核验、限制队列与并发 |
| 长期磁盘占用 | 减少数据编码、重复副本和内部空闲空间 | 数组/表格分别编码、无损压缩、按哈希去重、必要时核验后整理库文件 |
| 等待时间 | 下载、解码、压缩、落盘、核验分别慢在哪里 | 分阶段计时、避免重复导入、分区裁剪、选择合适压缩级别 |

分块主要降低同时驻留的内存，不保证文件更小；压缩会消耗 CPU；云端排队和带宽不能靠本地压缩消除。完整保留与只保存统计结果具有不同的信息量，必须分别提供，不能把丢弃原数据称为无损压缩。

## 已做的实验

代码：[数组基准](../benchmarks/benchmark_arrays.py)、[表格基准](../benchmarks/benchmark_tables.py)。完整机器记录在 [arrays-windows.json](../benchmarks/results/arrays-windows.json) 和 [tables-windows.json](../benchmarks/results/tables-windows.json)。

两套实验均为可重新生成的合成数据，不读取私人数据库，不下载真实气候资料。每个方案用独立子进程运行，核对完整解码值哈希，之后清理该实验生成的临时文件。MiB = 1,048,576 字节。

### 数组：同样的压缩文件，可以用更少内存生成和核验

数组为512×256×256个float32，解码值共128MiB；流式方法每次生成/核验2MiB。下面均使用gzip4+shuffle，相同形状、dtype和完整值SHA。

| 合成分布 | 处理方式 | 峰值工作集内存 | 文件大小 | 生成、哈希和写入耗时 |
| --- | --- | ---: | ---: | ---: |
| 平滑场加小噪声 | 整体加载及整体回读 | 313.91 MiB | 76.31 MiB | 5.325 s |
| 平滑场加小噪声 | 分块生成及分块回读 | 59.82 MiB | 76.31 MiB | 4.880 s |
| 高熵随机数组 | 整体加载及整体回读 | 314.80 MiB | 104.21 MiB | 8.186 s |
| 高熵随机数组 | 分块生成及分块回读 | 59.37 MiB | 104.21 MiB | 7.745 s |

本机这两个比较的峰值驻留内存降低约81%，文件大小一致、解码值逐字节一致。这里的“整体加载”基线特意同时保留原数组和一次完整解码副本，代表一种常见的完整回读流程，不是 v0.2 服务的实测峰值。数组文件使用HDF5内核，不包含完整NetCDF坐标与全部元数据。

### 压缩率、写入速度与查询布局要一起选择

- 平滑数组使用gzip1+shuffle为78.81MiB、4.426s；gzip4+shuffle为76.31MiB、4.880s。压缩等级应按实际负载选择。
- 平滑数组的gzip4关闭shuffle后为107.12MiB、9.713s。shuffle是字节重排，属于无损处理，不能与降低浮点精度混淆。[h5py过滤器说明](https://docs.h5py.org/en/stable/high/dataset.html#shuffle-filter)
- 改为空间小块、时间长块后，平滑数组降至68.45MiB，但写入增加到25.451s。高熵数组同样改块反而增至108.95MiB、36.694s，不能作为统一默认。
- 时间长块更适合单点长序列，时间短块更适合一幅区域小时图。查询测试先预热缓存，再取同一打开句柄三次读取的中位数；本轮单点与整图结果主要说明块布局和缓存的影响，不能当成冷启动读取或远程读取速度。

HDF5读取一个元素也可能解压其整个存储块；块形状需匹配实际查询。Zarr也需要匹配chunk与shard，堆积大量小文件可能增加文件系统/对象存储开销。[HDF5分块](https://docs.h5py.org/en/stable/high/dataset.html#chunked-storage)、[Zarr性能说明](https://zarr.readthedocs.io/en/stable/user-guide/performance/)

### 表格：二进制列式文件减少解析和无关扫描

1,048,576行合成表，包含时间索引、两个网格索引及两个float32列；原数值载荷20MiB。每批65,536行，四种格式的逐列完整值SHA相同。CSV回读与DuckDB导入都显式指定类型。

| 格式 | 文件大小 | 生成、哈希与写入 | 全表导入DuckDB | 筛选1,024行的查询中位数 |
| --- | ---: | ---: | ---: | ---: |
| CSV | 32.01 MiB | 2.112 s | 0.570 s | 439.56 ms |
| Parquet无压缩 | 16.94 MiB | 1.330 s | 0.086 s | 3.65 ms |
| Parquet ZSTD1 | 7.21 MiB | 1.488 s | 0.111 s | 5.62 ms |
| Parquet ZSTD9 | 7.18 MiB | 1.898 s | 0.087 s | 3.82 ms |

本轮ZSTD1相对CSV少约77.5%磁盘空间，全表导入约快5.1倍；ZSTD9只再少约0.4%文件空间，却增加写入时间。筛选查询利用了已排序时间索引和Parquet行组统计，CSV需要扫描解析更多内容；这不是任意查询均能获得的固定倍数。导入后另按时间顺序分批完整回读DuckDB，逐列SHA与原生成值一致，回读时间单独记录。[Arrow ParquetWriter](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetWriter.html)

DuckDB实验缓冲区设置64MB，但完整进程峰值工作集约190—220MiB（含排序与入库后的完整回读），另记录了提交内存。`memory_limit`不覆盖所有第三方和运行时内存，不能当作进程总内存上限。[DuckDB内存说明](https://duckdb.org/docs/1.5/guides/troubleshooting/oom_errors)

### 实验边界

单台Windows机器、单次方案运行；写入包括数据生成和哈希，未执行设备级冷缓存/持久写屏障。后台负载、另一套基准和OneDrive同步未隔离。合成数据的重复键、噪声、浮点位模式会影响压缩；不能据此承诺真实ERA5可压多少倍、100GB需多少时间或生产进程能固定在60MiB。

## 推荐落地结构

```mermaid
flowchart LR
    A[先定位来源与所需子集] --> B[有界获取或读取]
    B --> C[小块解码与时间/网格校验]
    C --> D[原类型无损压缩写入]
    D --> E[分块完整回读核验]
    E --> F[原子提交分区与来源清单]
    F --> G[按变量/地区/时间局部查询]
```

### 保存形态

1. **完整格点数组**：优先分区NetCDF4/HDF5，显式选择time/latitude/longitude块形状和gzip+shuffle。按月或合理文件大小分片，避免一个小时一个小文件；Zarr/sharding为经过实际负载测试后的备选。
2. **点位、站点和统计表**：候选为有明确schema的Parquet+ZSTD1—3。日期/地点/变量可筛选，不先转成Python字典列表或pandas整表。CSV、Excel作为按需导出。
3. **原始响应与来源**：如采用gzip保存响应原字节，同时记录压缩文件SHA和解压原字节SHA；不重新序列化JSON冒充原字节保留。原始档案与可查询结果分别记录，不能用结果摘要替代原件。
4. **统一索引**：数据库登记版本、范围、字段、分区位置和核验状态；查询可直接读取外部列式结果。私人研究库仍执行现有归档与完整核验协议，不能因目录存在就声称已入库。

### 有界执行

- 第一阶段只用一个写入工作进程，限制预取队列与解码/压缩并发；每个阶段都不能无界堆积块。
- 以2—8MiB解码块作为初始调优范围，按变量数量、源块布局及查询方式调整。单块大小不是总内存；额外计算解码副本、第三方缓存、压缩缓冲区与核验缓冲区。
- 生产目标先设为进程峰值RSS不超过512MiB，并同时监测提交内存与临时磁盘；这是**待实现/验收目标**。超过预算暂停下一块或缩小请求，不能靠强行分配失败维持“完成”状态。
- 远程排队时不占数据库写锁；数据到达并校验后用短事务提交。DuckDB可利用磁盘暂存处理部分超过内存的操作，但排序、分组等组合仍需测试。[DuckDB调优](https://duckdb.org/docs/1.5/guides/performance/how_to_tune_workloads)

### 降低总等待时间

- 分别记录远程等待、传输、解码、编码、落盘和完整核验的耗时；不能把源排队或全量SHA耗时计成某种压缩算法的性能。
- 先按地区/时间/变量裁剪，再传输和保存；区域统计应保留算法、边界、权重和UTC/当地日约定。
- 按明确来源、产品版本和请求身份复用已核验分区。中断后只补缺失部分，不重新导入全部历史数据。
- 从已有Parquet/NetCDF直接筛选查询，避免为一次查询重复解压整个ZIP或再复制进数据库。
- 优先测试较低压缩级别。已压缩的ZIP、JPEG、PDF和部分NetCDF可能收益很小，可能更慢或更大；不承诺统一压缩倍数。

## 实施顺序与验收门槛

| 顺序 | 改造内容 | 必须证明 |
| --- | --- | --- |
| 1 | 现有ERA5 writer/verifier改成有界分块，消除整批stack和完整重复回读 | dtype、坐标、UTC、单位、缺测政策、源值哈希与旧版一致；32MiB传输限额不冒充RSS限制 |
| 2 | 点位结果的新版本存储清单：原始响应无损压缩、列式查询副本、CSV按需导出 | 兼容读取旧manifest；原始字节与所有查询值可回读，现有文件不覆写或删除 |
| 3 | 长时段任务编排、分区状态、请求复用和断点恢复 | 每块独立核验、同源不重复、失败不标完整；既有单次请求限额仍有效 |
| 4 | 进程/暂存/输出预算控制，按访问模式选择块形状 | 实测完整进程内存，输出/暂存/队列有上限；规模增加不要求等比例增加RAM |
| 5 | 增大合成规模，再做明确真实气候子集验收 | 不把128MiB样本当作100GB验收；测试float32/float64、缺测、类型、空间/时间边界及故障恢复 |

v0.2已具备明确来源、ERA5批次、部分容量限制与来源核验。本页新增的是可复现实验和实施主线，**尚未把这些生产改造标为完成**。本阶段不重写私人数据库，也不自动删除或重新下载大批数据。

## 复现实验

安装项目的query可选依赖（提供Arrow和DuckDB），使用新的输出路径：

```sh
python -m pip install -e ".[query]"
python -c "from pathlib import Path; Path('data/benchmarks').mkdir(parents=True, exist_ok=True)"
python benchmarks/benchmark_arrays.py --output data/benchmarks/arrays.json
python benchmarks/benchmark_tables.py --output data/benchmarks/tables.json
```

脚本会创建并清理自己生成的合成临时文件；已存在的报告会拒绝覆写。数组实验单个临时文件约128MiB，实验依次运行；运行前应为库和运行时缓存预留额外内存/磁盘。
